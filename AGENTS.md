# T.R.S. (SCI0 port)

A port of "Trauma Response Simulator", a browser stat-management choice game, to Sierra's SCI0 engine (320x200
EGA, 1988-90 era) as a real, compilable game played straight as if Sierra shipped it in 1990. Interaction is
dialog choice lists plus a text parser in the office hub. Source is SCI Companion's C-like `.sc` dialect in `src/`,
compiled by SCI Companion 3 into `resource.map`/`resource.001` and run by the period interpreter `SCIV.EXE` under
DOSBox-X. The original browser game and the content generators live in a separate repository (see
`docs/ARCHITECTURE.md`, "Content pipeline").

This is the canonical instruction file for coding agents. `CLAUDE.md` imports it; do not duplicate these rules in
tool-specific files. Project facts belong in the documents linked below, not in an agent's private memory.

## Start here

1. Read `docs/HANDOFF.md` for the current state, active work, and gotchas.
2. Read the relevant roadmap item and the parts of `docs/ARCHITECTURE.md` and `docs/TESTING.md` that apply.
   Before touching any `.sc` file, skim `docs/SCI0-GOTCHAS.md`: most bugs this project has hit are listed there.
3. Inspect `git status` and recent history. Do not overwrite work you did not create.
4. Verify important inherited claims before relying on them. Use the fastest relevant check first.
5. State the intended scope briefly, then work on one independently reviewable change at a time.

If the request conflicts with these instructions or the working tree contains overlapping edits, stop and ask the
maintainer.

## While working

- Reference roadmap IDs where one exists. Do not invent an ID for an incidental, self-contained fix.
- Keep changes scoped. Do not mix opportunistic refactors with requested work.
- Preserve user changes. Never reset, clean, or rewrite history without explicit permission.
- Record a decision in `docs/DECISIONS.md` when reasonable maintainers could revisit the choice later.
- Update documentation in the same change when behaviour, interfaces, commands, or project structure change.
- Distinguish observed facts from inference. "Confirmed" means the maintainer saw it in a compiled game; say so,
  with the date. Code that has only been written, or only compiled, is not confirmed.
- Add newly discovered work to `ROADMAP.md` only when it is genuinely out of scope for the current change.

## Finishing a change

1. Run the checks appropriate to the change, following `docs/TESTING.md`. Record failures and anything not run.
   An agent cannot compile or play the game; say which in-game checks the maintainer still needs to do.
2. Review the diff for unrelated edits, stale names, and documentation drift.
3. Update `docs/HANDOFF.md` if work will continue in another session or if the repository's current state changed.
4. Update the roadmap item, decision record, and architecture only when their update trigger applies (see
   `docs/README.md`).
5. Run `python3 tools/check_docs.py` and report the result.

Do not manufacture ceremony: typo-only or mechanical changes do not need a decision or handoff rewrite unless they
alter a claim those documents make.

## Working agreement

Direct-to-master, single maintainer (Andrew Edmark). Agents edit files; the maintainer compiles in SCI Companion,
playtests, commits, and pushes. Agents do not commit, push, or add dependencies unless asked in the session.

- Default branch: `master`. Remote: github.com/aedmark/TRS_SCI (**public**: nothing private goes in tracked files).
- Commit format: free-form (the maintainer often uses the date, e.g. `09-15-26`).
- Release: zipped builds for itch.io, regenerated as needed (`*.zip` is gitignored).

Never force-push, rewrite shared history, publish, or delete the maintainer's save files without explicit
permission.

## Maintainer preferences

- **Writing:** plain, direct prose. In-game text is 1990 Sierra pastiche played completely straight.
- **Code comments:** what/how/why only. No debugging narrative, no references to handoff docs or playtests.
- **Asking vs. doing:** design changes to the player's flow (new prompts, anything asked before a session) need the
  maintainer's agreement first. Every pop-up must be escapable by a visible button.
- **Reporting:** say what was changed, what still needs compiling, and a short in-game checklist to confirm it.

## Engineering conventions

- Flat, early-return control flow: no `if/else` chains past one level, `switch` only on a plain variable,
  `and`-chains of at most 4 terms. No precedent exists for more; see `docs/SCI0-GOTCHAS.md`.
- Every script is either permanently resident or Load/Dispose-scoped; every call site into a scoped script has its
  own `Load(rsSCRIPT n)`/`DisposeScript(n)` pair. See `docs/ARCHITECTURE.md`, "Heap discipline".
- Fixed UI text goes in a text resource, not string literals: `text/*.txt` for new text.
- String literals are ASCII only, with no embedded `"`.
- Avoid creating a brand-new circular `(use ...)` pair; reuse an existing dependency chain instead.
- Generated files are committed. Regenerate, never hand-edit (see Protected areas).
- No dependencies beyond Node (for `tools/gen-text.js`) and Python 3 (for `tools/check_docs.py`).

## Run and verify

- Build: in SCI Companion, "Compile All", then "Rebuild Resources" (a batch of new scripts may need 2-3 rounds).
- Regenerate text: `node tools/gen-text.js` (verifies the patch it writes by reading it back).
- Run: `dosbox-x -c "MOUNT C \"$PWD\"" -c "C:" -c "SCIV.EXE"` from the repo root.
- Docs: `python3 tools/check_docs.py`.
- Detailed guidance and the in-game regression checklists: `docs/TESTING.md`.
