A Sierra-style trauma simulator

#
overviewplayer-facingSCI0

T.R.S. is a browser choice game rebuilt as a genuine late-SCI0 DOS game.

What it does

  1. Presents ten authored bad moments per standard session, each with three to five responses.
  2. Tracks Repression, Mask, and Child in the status line and resolves the run through one of 102 ending variants.
  3. Uses a Sierra-style office hub, dialog choices, and a typed text parser at 320x200 in 16-color EGA.

How it works

The period SCIV.EXE interpreter runs resources compiled from SCI Companion's C-like .sc source. Script 0 boots into the office, event rooms execute choices, and the ending room records the result before returning to the office.

Why it works this way

D-001 defines the project as a real, full SCI0 port rather than a visual imitation. That goal makes the interpreter's 16-bit arithmetic, 64KB heap, resource model, and era-appropriate interaction part of the design contract.

The office hub

#
player-facingparserroom

Every launch and completed session returns the player to a room where they choose when to begin again.

What it does

  1. Hosts one-time appearance and name setup, the filing cabinet for Case Files, the session computer, and the text parser.
  2. Lets the player back out of every office-opened pop-up with a visible control.
  3. Returns after boot, Restart Game, and every ending without forcing another session.

How it works

src/rm003.sc owns the room and parser. It loads scoped Case Files or prompt scripts only around use, reads fixed replies from TEXT_OFFICE, and starts src/rm001.sc only when the player confirms at the computer.

Why it works this way

D-004 replaced the old direct-to-event flow so the player has a stable in-world pause between sessions. Keeping one-time setup out of the recurring start flow preserves that control and matches the late-Sierra framing.

The ten-turn session loop

#
gameplayeventsstats

A session selects unseen events, applies a response, updates the stats, and ends at a bound or turn limit.

What it does

  1. Weights the next event zone toward the player's most endangered stat while preventing repeats within the run.
  2. Offers authored responses and sometimes an extra glitch response with random, untagged effects.
  3. Ends immediately if a stat reaches its bound or after the session's allotted turns.

How it works

src/rm001.sc resets run state and calls EndTurn(). Resident src/mechanisms.sc chooses a weighted zone and unseen room, clamps response effects, updates coping counts, and moves either to another event room or src/rm002.sc for the ending.

Why it works this way

The algorithm preserves the browser game's 2.5:1 pressure toward the worst stat while room transitions provide SCI0's safest cleanup boundary. SCI0-only random seeds are accepted because the browser's 32-bit generator cannot be reproduced faithfully with 16-bit arithmetic.

Choice dialogs and pagination

#
gameplayUIpagination

Event cards support all three-to-five authored responses within SCI0's compact dialog UI.

What it does

Displays up to three responses per page, adds More and Back navigation when needed, and returns a real response index or the special glitch value. Escape does not silently choose or dismiss an event.

How it works

Resident script 100 exposes PrintChoices. It paginates internally at CHOICES_PER_PAGE, draws the selected portrait mood, and translates page-local controls back into the caller's response index.

Why it works this way

Three visible choices fit the SCI0 dialog safely and legibly. Internal pagination gives every event one stable calling contract instead of making 196 generated rooms implement their own navigation.

Coping mechanisms

#
gameplayprogression

Repeated response patterns become unlockable run-level modifiers.

What it does

Tracks five tags—fawn, flight, fight, freeze, and secure—and unlocks a coping mechanism after three uses in one run. An unlocked mechanism passively modifies later effects and becomes discoverable in Case Files.

How it works

Authored choices carry a tag consumed by ApplyChoiceEffects in src/mechanisms.sc. Per-run counters trigger the modifier, while Case Files slots 102 through 106 retain discovery across runs.

Why it works this way

The system turns repeated response style into mechanics without adding a separate inventory or skill screen. Glitches remain untagged so random effects do not falsely express a deliberate coping pattern.

Persistent Case Files

#
persistenceprogressionheap

Endings and coping mechanisms discovered across runs remain available from the office cabinet and menu bar.

What it does

Stores 102 ending discoveries, five coping mechanisms, the Extended Therapy unlock, and the chosen appearance. Players can browse discovered entries by category and open a description.

How it works

src/CaseFiles.sc reads and writes 109 scalar slots in TRSCASE.DAT. The category UI and description dispatch are Load/Dispose-scoped, with description text split by pool so viewing one file stays within the fragmented 64KB heap.

Why it works this way

Cross-run discovery supplies long-term progression without changing the authored session loop. Scalar globals and per-pool scripts are awkward but match SCI0 visibility and heap limits; the prior category-sized description script exceeded the largest usable block after play.

Extended Therapy

#
gameplayprogressionnew-game-plus

Surviving once unlocks a longer, more intense New Game+ session.

What it does

Adds a 20-turn session option after the player survives a standard run and scales choice effects by 1.25. The unlock persists between launches.

How it works

A hidden Case Files slot records the survival unlock. The office computer then offers Standard, Extended, and Not yet; the chosen mode sets the turn limit and effect scale used by the resident turn-loop script.

Why it works this way

The mode extends mastered play using the same authored content and progression record. It replaces the browser game's arcade mode, which was deliberately cut because it did not fit the SCI0 port's product shape.

Persistent player portraits

#
player-facingUIpersistence

The chosen appearance follows the player into event dialogs and changes expression with the most endangered stat.

What it does

Offers four appearances once, saves the choice, and displays neutral, repression, mask, or child moods. The office mirror is the only normal way to choose again.

How it works

Views 801 through 804 each reserve loops 0 through 3 for the four moods. Case Files slot 108 stores the appearance as choice plus one, and GetPortraitMood() selects a non-neutral loop after the danger threshold is crossed.

Why it works this way

Persisting one selection avoids interrupting every session, matching the office-hub rule. Encoding zero as never chosen lets the same slot represent setup state without a second flag.

One room per event

#
architecturegeneratedheap

Each of the 196 authored moments is its own generated SCI room.

What it does

Maps WORK, HOME, SOCIAL, SELF, BODY, and PUBLIC events to rooms 200 through 395. Each room presents its choices, applies the selected effects, and hands control back to the common turn loop.

How it works

Browser-repository generators emit src/rm200.sc through src/rm395.sc. GoToNextEvent() computes a room from the selected zone base and local index, and newRoom lets the interpreter dispose the previous room at its normal boundary.

Why it works this way

D-002 replaced the earlier per-zone dispatcher because repeated manual load/use/dispose cycles fragmented the heap unpredictably. More scripts and manifest entries are a deliberate trade for reliable room cleanup.

64KB heap discipline

#
architecturememorySCI0

Scripts are explicitly resident or scoped, and every scoped call site owns a balanced load and dispose pair.

What it does

Keeps the always-needed turn and choice machinery resident while loading Case Files, prompts, endings, and large description pools only around use. It minimizes both peak memory and fragmentation-sensitive load cycles.

How it works

Every call into a scoped script has its own Load(rsSCRIPT n) and DisposeScript(n) pair. Case Files and its category browser never coexist, large text is split per pool, and buffers larger than a few hundred bytes live at script scope.

Why it works this way

SCI0's 64KB heap is the hard constraint behind the structure. Correct total size is not enough: after a run, fragmentation can leave no contiguous block for a large script, so transitions and load order must also be controlled.

Generated content and text pipelines

#
generationcontenttext

Bulk narrative content comes from the browser project; hand-written UI text is generated locally into SCI text resources.

What it does

Produces event rooms, ending pools, Case File descriptions, office text, and menu text in formats SCI Companion and the interpreter consume. Generated outputs are committed and must not be hand-edited.

How it works

The separate browser repository emits protected .sc files from its JavaScript content. In this repository, node tools/gen-text.js converts text/*.txt into loose text.NNN patches and matching index headers, then reads each patch back to verify it.

Why it works this way

Generation keeps 196 events and 102 endings aligned with the canonical browser content while avoiding unsafe manual transcription. Text resources keep fixed strings out of the heap, and loose patches avoid SCI Companion's editor limitations.

Build and run workflow

#
workflowbuildDOSBox-X

SCI Companion compiles and packs the game; DOSBox-X runs the resulting period interpreter and resources.

dosbox-x -c "MOUNT C \"$PWD\"" -c "C:" -c "SCIV.EXE"

What it does

Turns the tracked SCI source and resources into a playable DOS game, then launches that game in the supported runtime. Text and documentation generators can be run independently on the Linux host.

How it works

  1. In SCI Companion 3, open resource.map, choose Compile All, then Rebuild Resources; batches of cross-referencing scripts may need two or three shrinking-error rounds.
  2. From the repository root, launch SCIV.EXE through DOSBox-X with the mounted working directory.
  3. Run node tools/gen-text.js after text-source changes and python3 tools/check_docs.py after documentation changes.

Why it works this way

SCI Companion is the authoritative compiler for this dialect and resource layout, while DOSBox-X with the shipped interpreter is the only supported behavior target. Host-side checks catch deterministic source problems but cannot substitute for compilation and play.

Verification and evidence boundary

#
testingevidenceworkflow

A host check, successful compile, and maintainer playtest establish different levels of confidence.

What it does

Separates documentation consistency, text-resource round trips, compilation, and in-game behavior into explicit checks. Only a dated maintainer observation in the compiled game is called confirmed.

How it works

docs/TESTING.md maps each changed area to minimum checks and focused regression lists. Agents run standard-library and Node checks, report what was not possible, and leave SCI Companion compilation and DOSBox-X visual or behavioral checks to the maintainer.

Why it works this way

The Linux agent session cannot operate the Wine GUI compiler or see the game screen. Precise evidence language prevents source inspection or a clean static check from being mistaken for runtime confirmation.

The project documentation system

#
documentation3xworkflow

Purpose-built Markdown records remain authoritative while this manual supplies a searchable cross-cutting overview.

What it does

Routes current state, plans, architecture, decisions, tests, and SCI0 traps to separate owned documents. This manual connects selected subjects through explicit what, how, why, evidence, and related-entry fields.

How it works

docs/manual.json is the editable 3x source and docs/manual.html is generated by the vendored Python tool. python3 tools/check_docs.py validates the normal document graph, checks the manual, and fails if the committed HTML differs from a fresh build.

Why it works this way

D-007 stopped one handoff file from mixing durable and temporary knowledge. D-008 adds a newcomer-friendly reading path without making the generated manual a second authority for volatile state or exhaustive detail.
